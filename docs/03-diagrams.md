# Group Buying Uzbekistan — схемы MVP

Версия 1.0 · 15 сентября 2026. Схемы соответствуют [концепции](01-concept.md) и [ТЗ](02-technical-spec.md). Mermaid-блоки можно редактировать вместе с документами.

## 1. Общий процесс

```mermaid
flowchart TD
    A[Проверить поставщиков, пакет и платежную схему] --> B[Опубликовать группу]
    B --> C[Сбор возвратных платежей участия]
    C --> D{К дедлайну набрана цель?}
    D -- Нет --> X[Закрыть группу и вернуть платежи участия]
    D -- Да --> E[Закрытый сбор предложений и финальный раунд]
    E --> F{Есть минимум 2 допустимых предложения и цена в пределах?}
    F -- Нет --> X
    F -- Да --> G[Зафиксировать победителя и полную цену]
    G --> H[Покупатели подтверждают предложение]
    H --> I{Подтверждений достаточно?}
    I -- Нет --> J[Пригласить резерв в пределах срока предложения]
    J --> K{Минимум подтверждений достигнут?}
    K -- Нет --> X
    K -- Да --> L[Открыть индивидуальные счета поставщика]
    I -- Да --> L
    L --> M[Покупатели платят полную стоимость поставщику]
    M --> N[Сверить оплаты и вернуть платежи участия]
    N --> O{Достигнут оплаченный минимум?}
    O -- Нет --> P[Одно окно добора или согласие поставщика на меньший объем]
    P --> Q{Объем согласован по той же цене?}
    Q -- Нет --> R[Отмена: поставщик возвращает оплату товара]
    Q -- Да --> S[Зафиксировать оплаченный состав и обязательство поставщика]
    O -- Да --> S
    S --> T[Доставка и монтаж по отдельным заказам]
    T --> U{Заказ исполнен?}
    U -- Да --> V[Приемка и начисление комиссии]
    U -- Нет --> W[Обращение, устранение проблемы или возврат товара]
    V --> Y[Сверка и получение комиссии]
```

Отказ до оплаты товара запускает полный возврат платежа участия на любом предварительном этапе. После оплаты товара возврат товара ведется отдельно. Уже исполненные заказы не отменяются из-за проблемы другого покупателя.

## 2. Движение денег на одном заказе

```mermaid
sequenceDiagram
    autonumber
    participant B as Покупатель
    participant P as Платформа
    participant PSP as Платежный партнер платформы
    participant S as Поставщик
    B->>PSP: Платеж участия 200 000 сум
    PSP-->>P: Проверенное подтверждение платежа
    P-->>B: Участие подтверждено
    Note over P,S: Торги, выбор, подтверждения и открытие оплаты
    S-->>B: Счет на полную цену 4 290 000 сум
    B->>S: Полная оплата 4 290 000 сум
    S-->>P: Сверяемое подтверждение поступления с order_id
    P->>PSP: Запрос возврата 200 000 сум
    PSP-->>B: Возврат платежа участия
    PSP-->>P: Подтверждение результата возврата
    alt Оплаченный объем достаточен или меньший объем согласован
        P->>S: Зафиксированный состав оплаченных заказов
        S-->>P: Обязательство исполнить по зафиксированной цене
        S->>B: Доставка, монтаж и документы
        B-->>P: Подтверждение исполнения
        P->>S: Реестр и счет комиссии 128 700 сум
        S->>P: Оплата комиссии
    else Объем недостаточен и условия не согласованы
        P->>S: Отмена и реестр возвратов товара
        S->>B: Возврат 4 290 000 сум
        S-->>P: Подтверждение возврата для сверки
    end
```

Временная потребность покупателя: 4 490 000 сум. После возврата платежа участия итоговый расход при успешной покупке: 4 290 000 сум. Комиссия 128 700 сум — расчет при гипотезе 3%, до расходов и налогового учета. Платформа не переводит платеж участия поставщику и не называет этот маршрут escrow.

## 3. Независимые состояния

```mermaid
flowchart LR
    subgraph POOL[Группа]
        P1[COLLECTING] --> P2[SOURCING]
        P2 --> P3[OFFER_CONFIRMATION]
        P3 --> P4[PAYMENT_OPEN]
        P4 --> P5[FULFILLMENT]
        P5 --> P6[CLOSED: SUCCESS / PARTIAL / FAILED]
        P1 --> PX[EXPIRED]
        P2 --> PC[CANCELLED]
        P3 --> PC
        P4 --> PC
    end
    subgraph ORDER[Индивидуальный заказ]
        O1[AWAITING_PAYMENT] --> O2[PAID_WAITING_BATCH]
        O2 --> O3[RELEASED]
        O3 --> O4[Доставка и монтаж]
        O4 --> O5[COMPLETED]
        O2 --> OC[CANCELLED и возврат товара]
        O4 --> OR[Обращение / возврат товара]
        O5 --> OR
    end
    subgraph DEPOSIT[Отдельный платеж участия]
        D1[PENDING] --> D2[SUCCEEDED]
        D2 --> D3[Возврат REQUESTED]
        D3 --> D4[PROCESSING]
        D4 --> D5[Возврат SUCCEEDED]
        D4 --> D6[Сверка / повтор / оператор]
        D6 --> D4
    end
    O2 -. Основание вернуть платеж участия .-> D3
    PX -. Основание вернуть платеж участия .-> D3
    PC -. Основание вернуть платеж участия .-> D3
```

Возврат платежа участия не отменяет оплаченный заказ. Терминальный статус группы не означает, что все ее финансовые возвраты уже завершены.

## 4. Архитектура

```mermaid
flowchart TB
    UI[Лендинг и Telegram Mini App] --> API[Серверный API и проверка доступа]
    ADM[Операторская панель] --> API
    API --> CORE[Модульный монолит: группы, предложения, заказы, деньги]
    CORE --> DB[(Реляционная БД: данные, inbox, outbox, аудит)]
    DB --> WORK[Фоновый worker]
    WORK --> PSP[Платежный партнер: платеж участия и возврат]
    PSP --> CALLBACK[Проверяемый серверный callback]
    CALLBACK --> CORE
    WORK --> BOT[Telegram Bot]
    BOT --> BUYER[Покупатель]
    SUP[Реестр оплат и исполнения поставщика] --> VERIFY[Сверка финансовым оператором]
    VERIFY --> API
    CORE --> REPORT[Метрики, комиссии и расхождения]
    WORK --> ALERT[Очередь исключений и оповещение оператора]
```

API платежного партнера не используется для оплаты товара в выбранном MVP. Поставщик получает полную оплату по своему счету. Вебхуки и задачи допускают повторы; уникальные ключи и сверка защищают от повторного учета и возврата.

## 5. Основные связи данных

```mermaid
erDiagram
    USER ||--o{ PARTICIPATION : joins
    PRODUCT_SPEC ||--o{ POOL : defines
    POOL ||--o{ PARTICIPATION : contains
    POOL ||--o{ OFFER : receives
    SUPPLIER ||--o{ OFFER : submits
    POOL ||--o| WINNING_OFFER : selects
    OFFER ||--o| WINNING_OFFER : snapshots
    PARTICIPATION ||--o| ORDER : creates
    WINNING_OFFER ||--o{ ORDER : prices
    PARTICIPATION ||--o{ PAYMENT : deposit_attempts
    ORDER o|--o{ PAYMENT : goods_attempts
    PAYMENT ||--o{ REFUND : returns
    ORDER ||--o{ FULFILLMENT : tracks
    ORDER ||--o{ CASE : resolves
    ORDER ||--o{ COMMISSION_ENTRY : accounts
```

Для Payment обязательно указать purpose и recipient. Deposit связан с участием без обязательного заказа; GOODS связан с заказом и его участием. Временные неуспешные попытки допускаются, повторное исполнение одной внешней транзакции — нет.
